events, Pulse and email onto one project-information spine, so SiteWise can
answer "what changed on my project, and what needs me?"

**Architecture:** One canonical classification per document, produced once from
persisted extraction, consumed by every downstream workflow. Deterministic Python
owns validation and mutation; models only propose. Every mutation emits a project
event; Pulse reads events.

**Tech stack:** Python 3.12 + FastAPI · SQLAlchemy + Alembic · Supabase
Postgres/Storage/Auth · pgvector retrieval · React + Vite + TypeScript · FastMCP
at `/mcp` · Pi CLI agent runtime.

# 1. Core architectural principle

These features are not four subsystems. They converge into one spine:

```text
    uploads        email        future sources
        └─────────────┼─────────────┘
                      ▼
                EXTRACT ONCE  (raw source preserved)
                      ▼
           CANONICAL CLASSIFICATION
           class · subject · discipline · stage · confidence · basis
                      │
        ┌─────────────┼─────────────┐
        ▼             ▼             ▼
     EVIDENCE     FILE ROUTING   DOMAIN INTELLIGENCE
     retrieval    automatic      PMP · Cost · RFP/RFT · Tender
     citations    filing         Programme · Drawings · Consultants
                                 Invoice Review
                                      │
                                      ▼
                          VALIDATION / HUMAN REVIEW
                          deterministic checks, provenance
                                      ▼
                          AUTHORISED ACTIONS (REST + MCP, project-scoped)
                                      ▼
                              PROJECT EVENTS
                                      ▼
                               PROJECT PULSE
                       What changed? What needs me? What next?
```

The universal operating pattern:

```text
raw evidence → machine interpretation → deterministic validation
→ human review when required → authorised mutation → project event → Pulse
```

This is SiteWise architecture doctrine, not one feature's design.

# 2. Engineering principles

The binding, testable form of these lives in
[`00-doctrine.md`](./2026-08-18-pulse/00-doctrine.md) as D1–D11. Summary:

1. **One intake spine.** Ingest, Sort, invoice, tender and email must never hold
   disagreeing opinions about the same file.
2. **Extract once.** Parse and persist; every consumer reuses.
3. **Classification never removes evidence.** Text is indexed because it exists,
   not because a heuristic approved of the filename.
4. **Human overrides outrank machines**, permanently.
5. **Evidence and interpretation stay separate layers.**
6. **Models propose; Python verifies.**
7. **No autonomous sending or posting.**
8. **Converge, don't layer.** No `*_v2.py`. Classification LOC must not grow.

### Reconciliation with `AGENTS.md`

An earlier draft of this plan proposed six feature flags and temporary
compatibility shims. Root `AGENTS.md` forbids both ("No speculative feature
flags", "No backwards-compat shims unless explicitly asked for"). **`AGENTS.md`
wins.** Doctrine D9 records the resolution: no flags in Stages 1–8; compat reads
permitted only inside Stage 8, tracked in `TRACKER.md`, deleted before Gate 2.

# 3. Problems to fix first

All four verified against the codebase on 2026-08-18.

### 3.1 Sort Files appears to do nothing

`backend/app/intake/sort_service.py:~446` marks any file with
`ingest_status ∈ {pending, queued, ingesting}` as `skipped`. So: upload → see
files → press Sort → *0 moved*, with no explanation. Technically correct,
completely broken as UX.

### 3.2 Two classification systems

- `backend/ingest/classify.py` → `classify_entry()` decides *what a document is*,
  from filename and path only.
- `backend/app/intake/classifier.py` → `classify_inbox_destination()` decides
  *where it goes*, from its own regexes plus a 4096-byte content preview.

They share nothing. Target: `classify() → Classification → filing_destination()`.

### 3.3 Drawing classification suppresses searchable text

`classify.py` maps `drawing → register_only`; `ingest/router.py`
`should_persist_chunks()` then returns `False`. And `_looks_like_drawing()`
matches bare `\bplan\b` with only three exclusions — so `Cost Plan.pdf`,
`Business Plan.pdf`, `Payment Plan.pdf` and `Structural Specification Plan.pdf`
are classified as drawings and become **unsearchable**.

Note the text *is* extracted (PDF extraction precedes the drawing branch) and
then discarded at chunk time. The fix belongs in `router.py`.

### 3.4 Procurement stages are modelled as document classes

`tep`, `eoi`, `rft`, `addendum`, `tender_submission`, `evaluation`, `trr` are
stages, not forms. They belong in metadata.

### 3.5 Two undeclared classes exist in the database

`inbox_pending` (`app/api/projects.py:593`) and `corpus_catalog`
(`app/retrieval/catalog.py:110`) are written to `document_class` but are absent
from the `DocumentClass` Literal. Both are pre-existing type violations.

# 4. Canonical taxonomy

Frozen at Stage 3. Full vocabularies in
[`00-doctrine.md`](./2026-08-18-pulse/00-doctrine.md).

**`document_class`** — 11 values answering *"what kind of artefact is this?"*

| Class | Covers |
|---|---|
| `drawing` | plans, elevations, sections, details, sketches, mark-ups |
| `specification` | technical and written specifications |
| `report` | assessments, consultant reports, studies, surveys |
| `certificate` | approvals, determinations, consents, DCDs |
| `correspondence` | emails, letters, RFIs, notices, instructions, minutes |
| `contract` | appointments, deeds, agreements, subcontracts |
| `commercial` | invoices, fee proposals, tenders, quotes, claims, cost plans |
| `schedule` | registers, programmes, matrices, tabular artefacts |
| `statutory_instrument` | LEP, DCP, SEPP, NCC, Standards |
| `photo` | site, progress and condition photography |
| `unknown` | genuinely unresolved — still fully retrievable |

**`document_subject`** — 16 values on a second, independent axis: `planning`
`heritage` `structural` `services` `hydraulic` `fire` `geotechnical` `survey`
`cost` `programme` `contract_admin` `defects` `sustainability` `access`
`acoustic` `none`.

```text
Heritage Impact Statement  → report + heritage
Notice of Determination    → certificate + planning
Variation Claim 014        → commercial + contract_admin (commercial_type=variation)
```

Everything else — `discipline`, `commercial_type`, `procurement_stage`,
`confidence`, `basis` — lives in the `document_metadata` JSONB. **Do not create
a column per property.** `document_class` is `String(64)`, not a Postgres enum,
so the taxonomy change needs no schema migration.

# 5. Classification cascade

Cheap → expensive, stopping at the first confident answer.

| Stage | Signal | `basis` | Conf. |
|---|---|---|---|
| A | user override (project + content hash) | `user` | 1.00 |
| B | extension, native format, parsed title block | `structural` | 0.95 |
| C | **scored** filename/path rules | `filename` | 0.65–0.90 |
| D | deterministic markers in bounded extracted text | `content` | 0.80–0.95 |
| E | model fallback | `model` | *unbuilt* |

**Stage C must be scored, not first-match-wins.** The bare word `plan` is worth
1 point and can never decide a classification alone:

```text
Cost Plan.pdf                 commercial 7 · drawing 1  → commercial
A-102 Ground Floor Plan.pdf   drawing 10 · —            → drawing
Business Plan.pdf             drawing 1                 → no winner, fall to Stage D
```

Stage D uses the first ~4000 characters of *already-extracted* text. Never
re-open the file.

**Stage E is not built until measurement justifies it** (§10). Overrides from
Stage A become the labelled evaluation set.

Confidence bands: ≥0.90 very high · 0.75–0.89 high · 0.65–0.74 reviewable ·
<0.65 needs review. **Low confidence never blocks ingestion or indexing.**

# 6. Filing

Filing becomes a pure function of classification:

```python
filing_destination(classification, *, workspace_path, filename, project_workspace_path) -> str | None
```

```text
commercial + cost                   → 01-cost
report + structural                 → 03-design/structural
certificate + planning              → 04-planning-and-authorities
commercial + procurement_stage=rft  → 05-procurement
schedule + programme                → 06-programme
```

An explicit `_inbox/<PACKAGE>/` folder still wins — the user declared intent.
`INBOX_PACKAGE_DESTINATIONS` and discipline-slug inference are *routing*
knowledge and stay; the semantic regexes move into the classifier.

Normal behaviour becomes automatic:

```text
Upload → Reading… → Classifying… → Report · Structural · 92% → Filed → Design/Structural
```

Sort Files is retained only as an idempotent recovery action. It reads persisted
classification and moves files. It must never re-download or reclassify.

**Every file produces exactly one visible outcome:** `moved` · `already-filed` ·
`waiting` · `needs-review` · `unresolved` · `failed` · `skipped`. An unexplained
zero-result is a defect. When work is in flight, say so:

> 8 files are still being processed. They will be filed automatically when
> classification completes.

# 7. Invoice review

Extend `backend/app/cost_plan/` — the invoice engine already exists
(`invoice_extraction.py`, `invoice_mapping.py`, `invoice_service.py`,
`invoice_candidates.py`, `evidence_reconciliation.py`). A new package would
violate D8. **Do not adopt Azure Document Intelligence** just because the
`e2e-invoice-review` reference repo uses it.

**Keep:** durable workflow · construction cost mapping · remembered supplier
mappings · duplicate/conflict detection · cost-plan integration · provenance.

**Adopt:** immutable machine extraction · conditional secondary extraction ·
field-level reconciliation · explicit validation issues · editable reviewed
state · a hard approve/reject boundary.

### Immutable extraction

Machine-observed values (supplier, ABN, invoice number, dates, subtotal, GST,
total, line items, PO and variation references, source locators) are never
overwritten. Reviewed values live alongside:

```text
machine:  INV-1O42        reviewed: INV-1042
```

### Reconciliation

Fields carry `primary · secondary · reviewed · confidence · status · source ·
source location`, with status ∈ `match | different | missing_primary |
missing_secondary | missing_both`. Review focuses on **disagreements**, not every
field.

Secondary extraction runs **only** on: missing required field · low confidence ·
failed total validation · ambiguous line table · poor layout parsing · critical
field disagreement. Never a second model call for a clean invoice.

### Cost mapping stays construction-specific

Not generic GL coding. Remembered supplier mapping → exact cost-item match →
reference match → keyword scoring → confidence → explicit unmapped handling.

```text
Ardent Structural Engineers — Invoice 0421
  Structural engineering fee   $8,500  → Consultant Fees / Structural Engineer   98% remembered
  Additional redesign services $2,400  → Structural Engineer / Variations        72% review
  Printing                       $140  → Unmapped
```

### Validation issues

First-class, coded, with severity `error | warning | info`. Adapt existing
validators to emit them — do not write a second validation layer.

```text
TOTAL_MISMATCH · GST_MISMATCH · DUPLICATE_INVOICE · CONFLICTING_DUPLICATE
UNKNOWN_SUPPLIER · ABN_MISMATCH · UNKNOWN_COST_CODE · PO_NOT_FOUND
VARIATION_NOT_FOUND · UNAPPROVED_VARIATION · DATE_OUTSIDE_PERIOD
AMOUNT_EXCEEDS_COMMITMENT · COST_PLAN_OVERRUN · CLAIM_EXCEEDS_REMAINING_VALUE
MAPPING_LOW_CONFIDENCE
```

Validate against the **project**, not just the document: is the supplier
appointed? does the ABN match? does the PO exist? is the referenced variation
approved? does claimed-to-date exceed commitment? would approval move the
forecast? Example outcome:

```text
Ardent Structural — INV-421 — $11,990
✓ Arithmetic reconciles          ✓ ABN matches consultant record
✓ Appointment found              ✓ Previous invoices total $46,200
⚠ Additional services $2,400 reference VO-17
⚠ VO-17 has not been approved
⚠ Approval would increase Structural forecast by $2,400
Recommendation: Hold for review
```

### States and boundary

`received → extracting → ready_for_review → needs_attention → approved →
rejected → posted → duplicate → conflict`, with payment status
(`unpaid | scheduled | paid`) kept separate. Never conflate received / reviewed /
approved / posted / paid.

High-confidence invoices may reach `ready_for_approval`. **Nothing crosses the
approval boundary silently.**

Review UI is three panes — original · extraction · cost allocation — with
validation issues and Hold/Reject/Approve along the bottom. Uncertain fields show
primary, secondary, source location and an editable reviewed value.

Events: `invoice.received · classified · ready_for_review · needs_review ·
approved · rejected · posted · duplicate · conflict`.

# 8. Project events and Pulse

### Event spine

A lightweight semantic layer over existing project activity infrastructure.
Project-scoped, idempotent, deduplicated. Events reference canonical state —
**there is no second Pulse database.**

```text
document.received | extracted | classified | reclassified | filed | revised
invoice.received | needs_review | approved | posted | duplicate | conflict
email.received | linked | action_detected
project_signal.detected
```

### Signals

Derived, evidence-linked, never state-mutating:

```text
drawing_revision · approval_received · potential_cost_change · programme_risk
decision_required · consultant_action_due · unanswered_correspondence
tender_received · invoice_review_required · document_needs_classification
```

```text
type: potential_cost_change · source: Invoice 009 · value: 8400
confidence: 0.94 · status: open
```

### Pulse

Pulse answers **"What changed?"** — it is not an inbox.

```text
PROJECT PULSE                              3 items need attention

01 · STRUCTURE   Revised structural drawing received. S203 Rev C supersedes Rev B.
02 · COMMERCIAL  Builder Invoice 009 includes $8,400 against an unapproved variation.
03 · PLANNING    Notice of Determination received.

OTHER ACTIVITY   6 documents filed · 2 consultant replies · 1 invoice ready for approval
```

The failure mode to design against:

```text
48 emails · 26 documents · 12 events        ← never render this
      ↓
3 things changed · 2 decisions · 1 risk     ← always render this
```

Card actions (`View evidence · View thread · Ask SiteWise · Draft reply ·
Review invoice · Update programme · Resolve · Dismiss`) call existing domain
services. **No business logic in Pulse UI.** Reuse existing dirty-state concepts:
*"DA consent received. Update Planning and Programme?"*

# 9. Email

Begins only after canonical intake and events are stable. Provider-neutral:

```text
backend/app/email/{models,service,sync,project_matching,threading,attachments,actions}.py
backend/app/email/providers/{base,microsoft_graph,gmail}.py
```

### The rule that matters most

> **Email does not get its own attachment pipeline.**

```text
email attachment → canonical project intake → existing extraction
→ canonical classification → evidence → domain workflow
```

Manual upload and email receipt of the same invoice must produce **identical**
downstream behaviour. That equivalence is the acceptance test.

### Raw stays raw

Persist headers, sender, recipients, subject, timestamps, body, attachment
references, provider message and thread IDs — immutably. Summary, project match,
classification, signals, actions and cost/programme implications are derived and
stored separately. **Never replace raw correspondence with an AI summary.**

### Project matching

From known contacts, project address and number, historical thread association,
consultant domains, subject references, attachment metadata, and explicit user
corrections. Returns `project_id + confidence + basis`; low confidence goes to
review.

### Classification boundary

Email body is `document_class = correspondence` with an optional subject. The
semantic categories (`action_required`, `decision_required`, `design_change`,
`RFI`, `instruction`, `programme_change`, `document_transmittal`, …) are
**message/signal metadata — never document classes.**

### Intelligence, not automation

Commitments ("We will issue IFC drawings Friday"), cost signals ("Proceed with
Option B, additional cost $7,800") and decisions become **candidates with source
evidence**. No silent canonical mutation from stochastic inference.

### MCP boundary

Allowed: `search_project_email · read_email_thread · get_email_attachment ·
list_project_correspondence · create_email_draft · reply_email_draft ·
forward_email_draft · link_email_to_project`, plus `propose_email_action` and
`propose_project_decision`.

**Never exposed:** `send_email_unattended · delete_email ·
change_mailbox_rules · bulk_forward`, or moving arbitrary personal mail.

### Closed-loop procurement

```text
generate RFP/RFT → attachments → recipients → draft cover email → user approves
→ issue → track → detect returns → canonical classification
→ procurement_stage=submission → Tender Comparison → chase missing bidders
→ draft recommendation
```

The email domain must not duplicate procurement logic.

### Later: project aliases

`PROJECTCODE@in.sitewise.au` lets consultants simply CC SiteWise. Complements
rather than replaces Outlook/Gmail connections.

# 10. When the model fallback is allowed

After real usage, measure and record in `TRACKER.md`:

```text
unknown classification rate · user override rate (by class, by subject)
filename classifier accuracy · content classifier accuracy
secondary invoice extraction frequency · email project-match correction rate
```

Only then tune stochastic classification. **User corrections are the labelled
evaluation data** — which is why Stage 5 precedes Stage E.

# 13. Performance

```text
Avoid:  extract → model classify → re-extract → Sort parse → invoice parse → email parse
Target: extract once → persist → reuse
```

Embedding, classification enrichment and metadata extraction may run
concurrently. Deterministic dependencies stay ordered.

# 14. Migration safety

Every migration: forward · working `downgrade()` · pre-migration counts ·
post-migration counts · idempotent where possible · rollback rehearsed on a copy
before any shared database.

Do not remove legacy taxonomy values until all 14 consumers are migrated. Compat
reads are permitted **only** within Stage 8 and must be listed in `TRACKER.md`
§ Shims outstanding. A shim without a tracker entry is a defect; a shim that
survives Gate 2 has become the parallel system this plan exists to prevent.

# 15. Cleanup milestone

After canonical migration, delete: obsolete classification regexes ·
class-driven ingest-mode logic · redundant Sort Files content extraction ·
duplicate tender-discovery heuristics · redundant invoice-candidate heuristics ·
legacy pseudo-class handling · every compatibility shim. Then run the full suite.

**The repository must be simpler at the end than at the start:** one classifier,
one filing mapper, one evidence pathway, one review philosophy, one authorised
action boundary, one event/Pulse layer.

# 17. Product positioning

From:

To:

> A construction operating system that continuously understands what changed in

```text
47 EMAILS · 26 DOCUMENTS · 4 INVOICES
              ↓  SITEWISE  ↓
```

# 18. Delivery

Stages, packets, gates and agent ownership live in
[`2026-08-18-pulse/`](./2026-08-18-pulse/). Shape:

```text
        ┌ Evidence Safety (1) ┐
START ──┼ Classifier (3,4) ───┼──► GATE 1: contract frozen
        ├ Sort/Filing (6,7) ──┤
        └ Audit/Backfill (2) ─┘
                    ▼
        fan out: retrieval · PMP/Cost · procurement · programme
                 MCP/UI · invoice · filing            (Stage 9)
                    ▼
              GATE 2: canonical classification live (Stage 8)
                    ▼
              Event spine (13) ──► Pulse (14) ──► Email (15–19)
                    ▼
              GATE 3 ──► Closed-loop workflows (20–22)
```

**Order is a hard dependency, not a preference:** evidence safety → audit →
canonical classifier → deterministic rules → human override → consolidation →
auto-filing → taxonomy migration → workflow integration → invoice → events →
Pulse → email → closed loop.

Wave 1 is ~4 agents and largely sequential on single-owner seams. Wave 2 fans out
to 6–10 once the contract is frozen. The highest-risk mistake in the whole
programme is several agents refactoring classification, inbox, evidence,
workflows and MCP simultaneously.
