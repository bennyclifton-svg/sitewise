# Part A — Stages 0–8 as built

## What holds up

tested. Classifier B's semantic families really were deleted, not duplicated —

## The pattern behind the failures

**Gate 2's checklist was satisfiable without being true.** "All 14 consumers
read canonical classification" was *literally correct* — and the list came from
`01-ground-truth.md`, which never named `source_documents.document_type`. The
checklist was checked; the invariant was not. Three of the twelve findings
trace to trusting a derived list over the doctrine.

Second pattern: **the plan sometimes specified the bug.** Stage 5.3's sketch
literally contains `document_metadata={"basis": "user", "confidence": "1.0"}` —
the exact line that destroys machine metadata. The implementer followed the
plan faithfully. Stage 8B says so explicitly, so nobody "restores" it.

## B1 — Stage 12.2 contradicted its own security pattern *(fixed)*

12.2 specified `cross-project actor → 403` while telling the agent to copy the
authorization pattern from Stage 5.4 — which says, in bold, *"404, not 403 — do
not leak existence across tenants."* A 403 on another project's invoice confirms
that invoice exists.

Fixed in place with a status table: 404 for cross-project and non-owner, 409 for
open error issues and illegal transitions. This was the single highest-severity
finding in Part B.

## B2 — Stage 9.6 misdescribed its target *(rewritten)*

The task said "Modify `mobilisation_evidence.py` (path/filename markers)". Two
things are wrong:

- It has **no path or filename markers**. Its markers are content scrapers over
  concatenated text (`"heritage impact statement" not in lowered`,
  `mobilisation_evidence.py:492`) that extract advice *prose* into structured
  fields. Replacing them with `subject == "heritage"` deletes the extraction.
- Its signature is `(source_texts: list[str], evidence_refs, source_labels)`. It
  never sees a `SourceDocument`, a class, or a subject. Making it
  classification-aware means changing four call sites, one of which
  (`create_pmp.py:1277`) carries a pre-existing baseline failure that would mask
  any regression.

The real gap is **selection**: `pmp_sweep.py:187` sweeps every active document
up to a cap with no ranking. Rewrote the packet to rank the sweep by
classification and leave the extractors alone.

## B3 — Stage 9.5 was under-scoped *(scope corrected)*

`is_invoice_document(*, filename: str, content: str)` has no access to the
document. "Read `document_class` and `commercial_type`" is a signature change
plus four call sites — and one of them, `invoice_extraction.py:50`, sits in a
file **Stage 11 owns**. Left unstated, two agents collide.

Added the call-site table and an explicit ownership carve-out: 9.5 owns that one
line for the signature change only, and must Integration-note it.

## B4 — Stage 10.3 named one blocker; there are three *(corrected)*

"Relax `ck_cost_invoices_total_reconciles`" handles `subtotal + gst != total`.
It does not handle `ck_cost_invoices_positive_amounts`
(`subtotal <= 0 OR gst < 0 OR total <= 0`) or the non-positive branch of
`reconcile_totals` — and a scanned invoice with a missing subtotal trips those,
not the reconciliation check. Added all three with a recommended resolution
(untrusted numbers live in JSONB; typed scalars keep both constraints).

## B5 — Stage 10.2's overlay is wrong for `lines` *(guard added)*

`{**machine, **reviewed}` is a shallow merge and `ExtractedInvoice.lines` is a
list. Any overlay containing `lines` replaces every machine line wholesale,
silently discarding lines the reviewer never opened. Added the decision and a
failing test; recommended keeping `lines` machine-owned until a stable line
identity key exists (list index will not do — a re-extract reorders them).

## B6 — Stage 11 needed a column it had no authority to create *(resolved)*

11.1 stores `cost_invoices.issues JSONB`, but Stage 11's Ownership block lists
no Alembic revision, and migration ordering is a declared single-owner seam.
Moved the empty column into Stage 10.1's migration; Stage 11 now fills it and is
told to stop and Integration-note if it is missing.

## B7 — Stage 9's predecessor was incomplete *(updated)*

9.3, 9.4 and 9.5 all assert on `document_metadata` that Finding 1 wipes. Writing
those tests against today's behaviour would bake the bug into the regression
suite. Predecessor is now Stage 8 → **Stage 8B Wave A** → Gate 2 signature →
9.1.

# Part C — Stages 13–22 as planned (added 2026-08-19, second pass)

Reviewed after Stages 8B–12 landed. **Every file path, symbol, constraint
name and Alembic head these ten files cite was checked against the working
tree and is correct** — including the prediction that head would be
`051_invoice_review_state`. The vocabulary discipline is right throughout:
`message_category` stays off `DocumentClass`, TCM stays unmerged, Pulse gets
no table, no stage invents a feature flag.

The corrections are about **execution hazards** — places where a competent
agent following the text would produce working-looking code with a latent
defect. All fixed in place.

## C1 — Stage 13: the dedup no-op would have been a silent swallow

`record_activity_events` already wraps inserts in `session.begin_nested()`
and **catches every exception**, logging `activity_events_record_failed`
(`app/database/activity_events.py:96-118`). Routing verbs through it means a
dedup collision logs an ERROR on every re-ingest, a *genuine* failure is
invisible, and `test_duplicate_dedup_key_is_noop` passes even if the unique
index is dropped. Specified `INSERT … ON CONFLICT DO NOTHING RETURNING`
instead, with the partial-index `index_where` predicate that Postgres
requires and that fails only at runtime.

## C2 — Stage 13: `run_id` is NOT NULL and the sketch never set it

`ActivityEvent.run_id` is `nullable=False` with no default. The
`record_project_verb` sketch omits it entirely — first call, IntegrityError.
Policy added: fresh `uuid4` per verb.

## C3 — Stage 14: attention was unbounded, defeating the stage's own goal

`document_needs_classification` fires on a **standing population** (every
`unknown` or sub-threshold document), not on events. The stage opens by
promising "3 items need attention" and forbidding `48 emails · 26 documents`
— then defines `attention: list[PulseItem]` with no cap and no grouping. On
a real corpus that renders as hundreds of cards, which is the same failure
in a different costume. Added `MAX_ATTENTION_ITEMS` / `MIN_GROUPED`,
group-then-cap ordering, pre-truncation `attention_count`, and four tests.

## C4 — Stage 14: dismissal was permanent for mutable subjects

`invoice_review_required:cost_invoice:{id}` dismissed once hides that
invoice forever — including after new `severity=error` issues land.
Resolved by appending a state discriminator to subject keys derived from
mutable rows, in 14.1's key builder rather than per detector.

## C5 — Stage 19: sending was a dual write that duplicates mail

"Call `provider.send_draft` then set `status=sent`" leaves a window where
the provider accepted the message and the commit failed. The user retries;
the consultant gets it twice; email cannot be unsent. Replaced with
claim-then-send (`draft → sending → sent | send_failed`), `SELECT … FOR
UPDATE` to stop concurrent sends, and no auto-retry — a stuck `sending` row
is surfaced to a human, because only the mailbox knows the answer.

## C6 — Stage 20.2 gave two contradictory orders in one paragraph

It said "Order: send then transition", then "Prefer: transition first … roll
back on send failure", then "**Choose DB-then-send**". Rewritten as an
explicit five-step sequence built on Stage 19.2's now-safe send. Send-first
is correct *because* C5 made sending safe: the email is irreversible, the
request status is local and re-derivable. Issuing first would leave a
request marked `issued` when nothing was sent — the worse failure.

## C7 — Stage 16: the equivalence assertion would have failed for the wrong reason

`machine_extraction A == B` as raw JSON equality breaks on provenance
locators, per-field confidence, and timestamps. An agent hitting this red
test is most likely to "fix" it by loosening the comparison — gutting the
programme's non-negotiable email rule. Added a normaliser with a deliberately
small `VOLATILE` set, plus separate explicit assertions on the money fields
so they can never be normalised away.

## C8 — Stage 17: re-import would silently wipe user links

The exit gate demands "user correction survives re-import", but nothing
stopped `import_provider_messages` writing a default interpretation on every
pass. That is Finding 1 from Part A reappearing in email. Added
`ON CONFLICT (email_id) DO NOTHING` and a refusal to downgrade
`basis="user"`.

## C9 — Stage 15: three schema decisions left open

`content_hash` had no defined input (making it provider-specific and useless
for dedup), `sent_at NOT NULL` discards messages with malformed `Date`
headers, and the raw-immutability guard was service-level only — bypassed by
any `session.execute(update(...))`. Settled all three; the guard is now a
mapper `before_update` listener.

## C10 — Stage 13.5: revision ordering and an unindexed JSONB lookup

"A different revision exists" is not "a newer revision arrived" — uploading
Rev B when Rev C is on file is a late arrival, not a revision. Naive string
compare also puts `Rev 10` before `Rev 9`. Added both tests, plus a note to
`EXPLAIN` the `document_metadata->>'drawing_number'` lookup, which runs on
every drawing ingest against an unindexed expression.

## C11 — Stage 22: unauthenticated memory exhaustion

`attachments[{content_base64}]` inlines every attachment into one JSON body
that FastAPI materialises before the handler runs — and the HMAC is checked
after. Added size → signature → parse → ingest ordering, 413 before parsing,
and a test that the signature is verified against raw bytes rather than
re-serialised JSON (which passes your own tests and fails every real sender).
