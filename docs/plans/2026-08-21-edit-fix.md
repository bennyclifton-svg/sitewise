## SiteWise Editing Architecture — Implementation Plan

### Objective

Make PMP, RFP and RFT editing **deterministic, fast and immediately responsive**.

All user edits must appear in the UI instantly, without waiting for a server round-trip. The same editing architecture must support:

- inline text editing;
- table-cell editing;
- add row above;
- add row below;
- delete row;
- add/delete paragraphs or list items;
- future move/reorder operations;
- AI edits;
- preservation of manual edits during later AI updates;
- undo/retry/error recovery.

The user should feel they are manipulating the project directly, not editing a Markdown document.

---

## 1. Replace range-based identity with stable block IDs

Every editable document element must have a permanent unique ID.

Examples:

```ts
blk_paragraph_123
blk_row_456
blk_risk_789
```

Change block targeting from:

```ts
{
  range: { start, end }
}
```

to:

```ts
{
  id: "blk_row_456",
  type: "table_row"
}
```

Character ranges may still be calculated for Markdown rendering but must **never be the authoritative identity used for mutations**.

Apply this to:

- paragraphs;
- headings;
- bullets;
- numbered items;
- table rows;
- table cells;
- schedules;
- risk registers;
- procurement items;
- other structured PMP/RFP/RFT content.

---

## 2. Introduce one shared block-operation API

All human and AI edits should use the same mutation layer.

Support:

```ts
INSERT_BEFORE
INSERT_AFTER
UPDATE
DELETE
MOVE
REPLACE_SECTION
```

Example:

```ts
{
  operation: "INSERT_AFTER",
  block_id: "blk_row_456",
  content: {...},
  base_version: 37,
  client_operation_id: "op_xyz",
  origin: "user"
}
```

Avoid special editing implementations for PMP versus RFP versus RFT.

Build one reusable document-editing engine.

---

## 3. Make every user operation optimistic

**The UI changes first. The server confirms second.**

For example, Add Row Below:

```text
Click Add Row
      ↓
New row appears immediately
      ↓
Cursor automatically enters first cell
      ↓
User continues working
      ↓
Save happens asynchronously
```

Do not:

```text
click
→ API request
→ wait
→ reload document
→ finally display row
```

Target interaction latency should effectively feel instantaneous — ideally under one animation frame for the local UI update.

---

## 4. Use temporary IDs for newly created content

When inserting a new block:

```ts
tmp_83ac7
```

Render it immediately.

When the server confirms:

```text
tmp_83ac7
   ↓
blk_9012
```

Replace the temporary ID silently without re-rendering the entire document.

The user's cursor/focus must remain intact.

---

## 5. Fix table editing comprehensively

Implement these operations through the common block system:

```text
Add row above
Add row below
Delete row
Edit individual cell
Edit full row
Duplicate row
```

A table row should be structured internally:

```ts
{
  id: "blk_row_456",
  type: "table_row",
  cells: {
    consultant: "...",
    scope: "...",
    status: "..."
  }
}
```

Do not manipulate tables primarily using Markdown `split("|")` and character-string replacement.

Serialize the structured table back into Markdown only when required.

---

## 6. Direct inline editing

Enable:

```text
Double click paragraph
        ↓
Text becomes editable in place
        ↓
User types
        ↓
UI updates immediately
        ↓
Autosave
```

The document must not jump, refresh or disappear while saving.

Use approximately:

```text
300–500 ms debounce
```

for ordinary typing saves.

Pressing Enter, clicking elsewhere, or leaving the block should flush pending changes immediately.

---

## 7. Never hide content while saving

Remove the current behaviour where editing/composer state can disappear before persistence completes.

Instead use lightweight state indicators:

```text
Saving…
Saved
Save failed — Retry
```

Do not block further editing while one block is saving unless there is a genuine conflict.

Users should be able to rapidly:

```text
add row
edit row
delete another row
edit paragraph
add another row
```

without waiting for each operation to finish sequentially.

---

## 8. Never silently fail

Remove silent no-op behaviour when ranges or document state are invalid.

Any mutation failure must:

1. preserve the user's local content;
2. show an unobtrusive error;
3. allow Retry;
4. log diagnostic information;
5. never revert the UI without explanation.

Example:

```text
Couldn't save this change. Retry
```

The typed content should remain visible.

---

## 9. Add document versioning and conflict handling

Every mutation carries:

```ts
base_version
```

Server returns:

```ts
new_version
```

When versions conflict, resolve by **block ID**, rather than replacing/reloading the entire Markdown document.

For unrelated blocks, merge automatically.

For a genuine same-block conflict, preserve both states and flag it rather than silently overwriting either one.

---

## 10. Protect manual user edits

Track provenance on every block:

```ts
{
  origin: "generated" | "user" | "ai",
  userEdited: true,
  userProtected: true
}
```

Once a user manually modifies generated content, subsequent AI regeneration must not silently overwrite it.

AI should either:

```text
preserve
merge
propose replacement
flag conflict
```

depending on the operation.

---

## 11. AI edits must use exactly the same block API

Do not let AI regenerate whole Markdown documents to perform normal editing.

An AI instruction such as:

> Add the landscape architect to the consultant schedule.

should resolve to:

```ts
INSERT_AFTER(...)
```

Likewise:

> Change the architect's scope.

becomes:

```ts
UPDATE({
  block_id: "blk_row_456",
  field: "scope",
  ...
})
```

And:

> Remove this obsolete risk.

becomes:

```ts
DELETE({
  block_id: "blk_risk_789"
})
```

This makes AI edits predictable and preserves surrounding user changes.

---

## 12. Separate document state from Markdown rendering

Longer term, use:

```text
Structured document state
          ↓
 UI/editor
          ↓
 Markdown serializer
```

rather than:

```text
Markdown string
      ↓
find character ranges
      ↓
splice strings
```

Markdown can remain the stored/export format if desired, but it should not be the primary editing model.

---

## 13. Avoid full-document reloads after normal edits

After a successful mutation, update only the affected block.

Do not routinely:

```text
save
→ fetch entire latest draft
→ parse everything
→ rerender document
```

Use server responses to update the canonical local state incrementally.

Full reconciliation should be a fallback mechanism, not the normal editing workflow.

---

## 14. Add undo/redo-ready operation history

Store local operations:

```ts
{
  operation_id,
  block_id,
  before,
  after,
  timestamp
}
```

Design this so `Ctrl+Z` / `Cmd+Z` can be introduced cleanly.

Even if full undo/redo is deferred, don't build the new mutation engine in a way that prevents it.

---

# Implementation sequence

**Stage 1 — Immediate UX stabilisation**

Fix Add Above/Below, Delete and inline editing. Keep optimistic edits visible during saving. Remove silent mutation failures. Add regression tests for the current PMP table bug.

**Stage 2 — Stable block architecture**

Make block IDs mandatory. Implement the shared `INSERT / UPDATE / DELETE / MOVE` mutation API. Stop using character offsets as persistent mutation targets. Add versioned/idempotent operations.

**Stage 3 — Structured tables and document blocks**

Represent table rows/cells and other structured content as data objects internally. Reduce Markdown string manipulation to serialization/rendering only.

**Stage 4 — AI integration**

Move all AI edits onto the same block-operation system. Add provenance, protection and conflict rules so AI changes cannot unintentionally destroy manual edits.

---

## Acceptance criteria

The implementation is complete when a user can rapidly manipulate a PMP, RFP or RFT—adding rows, deleting them, inserting above/below, editing cells and double-clicking text—**with every action visible immediately and no document refresh or waiting state interrupting their flow**.

Normal editing should behave like a modern collaborative editor:

```text
USER ACTION
    ↓
IMMEDIATE LOCAL RESULT
    ↓
ASYNC PERSISTENCE
    ↓
SERVER CONFIRMATION
```

not:

```text
USER ACTION
    ↓
SERVER
    ↓
RELOAD
    ↓
UI RESULT
```

That responsiveness requirement should be treated as a core architectural constraint, not merely a UI enhancement.
